# 🗞️ Issue #012: Git Sorcery: Rewriting History Without Losing Your Mind

![The Terminal Thursday](https://images.vialoops.com/cmpfndk6x026w0jvslad39ftq/cmv8yi3q00f3w0j044w2njxiz.jpg)

Most of us live in a five-command subset of git: add, commit, push, pull, and a quiet prayer. Everything else gets treated like a live wire. Take interactive rebase: you edit a text file of verbs like `pick`, `squash` and `drop`, git replays your commits one at a time, and the first conflict stops it halfway through. The safety nets are real, since `git rebase --abort` returns your branch to its original state and the reflog remembers where it used to point. But nobody advertises them, so the history fills up with "wip", "fix", "fix again" and "actually fix", and whoever runs `git bisect` six months from now pays the bill.

The answer isn't to memorize more flags. Git's data model is fine; its controls are the problem, and a newer generation of tools replaces the controls without touching the engine. Jujutsu keeps your commits in a Git repository but treats rewriting them as an everyday operation, with an undo log behind it. Difftastic compares syntax trees instead of lines, so a reformat stops burying the one real edit. Delta makes the diff itself readable, and git-absorb works out which commit each fix belongs to. None of them needs your teammates to switch, because what reaches the remote is still ordinary git commits.

Grab your coffee. Open your terminal. Let's start hacking.

## 🔬 The Sandbox: 3 Projects I Tested This Week

### 1. Jujutsu 🥋 *(Version Control)*

![Jujutsu](https://images.vialoops.com/cmpfndk6x026w0jvslad39ftq/cmw1vzbdp2qzh0jyoafji2jhu.png)

**What is it?** Jujutsu (command: `jj`) is a version control system written in Rust under the Apache 2.0 license that keeps its commits and files in an ordinary Git repository, so it works with any Git remote and, in a colocated checkout, side by side with `git` itself. Its model differs from Git's in a few basic ways: the working copy is itself a commit that is amended automatically, there is no staging area, and every change keeps a stable ID while its commit hash changes on each rewrite. Martin von Zweigbergk started it as a hobby project in late 2019; Google is a main contributor, but the README is explicit that it is not a supported Google product.

**Why you should care:**  
Edit a commit anywhere in your stack and every descendant is rebased automatically; conflicts get recorded in the commits instead of freezing you halfway through a rebase, so you resolve them when you choose to. Every operation lands in an operation log, so `jj undo` takes back the last one (a botched rebase included), while `jj split` and `jj squash -i` carve and recombine commits without a todo list. Try it in a throwaway clone first, since the README still calls Jujutsu experimental and the docs list Git hooks as unsupported.

**My Rating:** Black-Belt Undo 4.8/5 ⭐  
**Website:** [github.com/jj-vcs/jj](https://github.com/jj-vcs/jj)

**💻 Get Started:**

```
brew install jj && jj git init && jj log
```

### 2. Difftastic 🔮 *(Structural Diff)*

![Difftastic](https://images.vialoops.com/cmpfndk6x026w0jvslad39ftq/cmw1vzcxu2r4x0j0e8mbzhvdm.png)

**What is it?** Difftastic is a diff tool written in Rust under the MIT license that detects the language, parses both files with tree-sitter grammars, and compares the syntax trees instead of the lines. Because it compares trees, a method chain reflowed onto new lines comes out as unchanged, and the matching itself is a route-finding problem on a graph that it solves with Dijkstra's algorithm. For file types it doesn't know, and for extremely large inputs, it falls back to a line-based diff with word highlighting.

**Why you should care:**  
Formatter commits, re-indented HTML and reflowed call chains stop burying the one real edit in review, and a file that was only reformatted just prints "No syntactic changes." Run `git -c diff.external=difft diff` in any repo with uncommitted changes (add `--ext-diff` for `show` and `log -p`), or wire it into Jujutsu with a two-line `diff-formatter` setting. The README is upfront about the trade-offs: the output is for humans and can't be applied as a patch, and it scales poorly on files with a large number of changes.

**My Rating:** Crystal-Ball Diff 4.7/5 ⭐  
**Website:** [github.com/Wilfred/difftastic](https://github.com/Wilfred/difftastic)

**💻 Get Started:**

```
brew install difftastic && git -c diff.external=difft diff
```

### 3. Delta ✨ *(Diff Pager)*

![Delta](https://images.vialoops.com/cmpfndk6x026w0jvslad39ftq/cmw1vzebu2r510jxib9c48w8k.png)

**What is it?** Delta is a syntax-highlighting pager for git, diff, grep and blame output, written in Rust under the MIT license. Git pipes its output through it, and it re-renders the diff with the same syntax themes as bat, word-level highlights inside changed lines (via a Levenshtein edit-inference algorithm), optional side-by-side panes and line numbers. The package is called `git-delta` in most package managers, but the executable is just `delta`.

**Why you should care:**  
Set `core.pager = delta` once and your `git diff`, `git show`, `git log -p` and `git blame` output comes out highlighted, with `n` and `N` jumping between files once `navigate = true` is set. Its improved merge-conflict display helps mid-rebase, and code copied out of a diff arrives without the `+` and `-` markers. It also ships an emulation mode for diff-so-fancy, and Jujutsu's docs show the config for using delta as its pager.

**My Rating:** Syntax Potion 4.6/5 ⭐  
**Website:** [github.com/dandavison/delta](https://github.com/dandavison/delta)

**💻 Get Started:**

```
brew install git-delta && git show | delta --side-by-side
```

## ☕ The Curious Non-Dev: No Code Required

**What actually is a commit, and how can you "rewrite history" without losing anything?**

A commit is a snapshot, not a list of edits. Each one stores the full state of a project at one moment, plus a note, an author, a timestamp and a pointer to the commit that came before it. Picture a stack of dated photographs of a whiteboard, each stapled to the one beneath it and stamped with a fingerprint computed from its own contents and the fingerprint below. A branch is just a sticky flag on one photo, and the flag is what moves when you add a new one. That chaining makes history tamper-evident: change one photo and its fingerprint changes, and so does every fingerprint stacked above it.

So "rewriting history" never edits a photo in place. It reshoots from the photo you want to change upward, staples the new stack onto the old base, and moves the flag to the top of the new stack. The old stack isn't shredded: git keeps a local log of where every flag used to sit, called the reflog, and by default it holds on to old positions for at least 30 days. That's how a botched rewrite gets undone. The golden rule is to do this before you share. Once colleagues hold copies of the old photos, two competing versions of the story exist, and somebody has to reconcile them.

## 📡 The Radar: 12 More Spells for Your Git Grimoire This Weekend

### 🪚 History Surgery

1. [tummychow/git-absorb](https://github.com/tummychow/git-absorb) (~5.8k Stars) - A Rust port of Facebook's hg absorb: stage your review fixes, run it, and it writes a fixup! commit for each hunk, aimed at the commit that should own it.
2. [newren/git-filter-repo](https://github.com/newren/git-filter-repo) (~13.5k Stars) - A single Python script for rewriting a whole repository's history, recommended by the git project over filter-branch and the tool GitHub's docs use for purging files from every commit.
3. [arxanas/git-branchless](https://github.com/arxanas/git-branchless) (~4.1k Stars) - Adds git undo (commits, amends, merges, even rebases), a smartlog view of your commit graph and in-memory rebases to plain git; the README still labels it alpha.
4. [git-town/git-town](https://github.com/git-town/git-town) (~3.4k Stars) - A Go CLI that turns branch chores into commands (hack, sync, propose, ship), with stacked-change helpers like append and prepend and an undo for its own commands.

### 🖥️ Git in Your Terminal

5. [jonas/tig](https://github.com/jonas/tig) (~13.4k Stars) - A text-mode git repository browser written in C, first committed in April 2006, that also stages changes chunk by chunk and doubles as a pager for other git commands.
6. [gitui-org/gitui](https://github.com/gitui-org/gitui) (~22.6k Stars) - A keyboard-only terminal UI in Rust for staging single hunks or lines, stashing and searching the log; interactive rebase is still on its roadmap to 1.0.
7. [so-fancy/diff-so-fancy](https://github.com/so-fancy/diff-so-fancy) (~18.1k Stars) - A Perl script that makes diffs human-readable by stripping the leading +/- markers and simplifying hunk headers; delta even ships an emulation mode for it.
8. [dlvhdr/gh-dash](https://github.com/dlvhdr/gh-dash) (~12.7k Stars) - A gh extension that turns pull requests and issues into a keyboard-driven dashboard of sections you define per repo, built on Bubble Tea and using delta to render PR diffs.

### 🤝 Hooks, Changelogs & Releases

9. [pre-commit/pre-commit](https://github.com/pre-commit/pre-commit) (~15.7k Stars) - A package manager for git hooks: list them in .pre-commit-config.yaml and it fetches each hook's toolchain without root, even downloading and building node to run eslint.
10. [evilmartians/lefthook](https://github.com/evilmartians/lefthook) (~9.0k Stars) - A dependency-free Go binary from Evil Martians that runs your git hooks from a lefthook.yml, in parallel, with glob filters and a list of just the staged files for each job.
11. [orhun/git-cliff](https://github.com/orhun/git-cliff) (~12.3k Stars) - Writes your changelog from git history using conventional commits or regex parsers, with the output shaped by a template and a cliff.toml you control.
12. [cli/cli](https://github.com/cli/cli) (~46.8k Stars) - GitHub's official gh: pull requests, issues and other GitHub concepts in the terminal, right next to your git workflow, and pre-installed on GitHub-hosted runners.

## 🏗️ Closing Thoughts

Some of the best ideas in this issue weren't invented for git. git-absorb ports a Facebook Mercurial command, Jujutsu cites Mercurial's revsets and Darcs' first-class conflicts as inspirations, and git-branchless goes after an undo that covers a whole repository instead of one ref at a time. Git stays the storage layer underneath while the ergonomics arrive from other version control systems, which is a decent argument for reading about ones you'll never use.

One warning before you go rewrite everything. A tidy history is a kindness to your reviewers, but rewriting isn't erasing, because clones and forks keep the old commits, so GitHub's docs say to revoke or rotate a leaked secret first. And once you've pushed, treat the history as published. If you must rewrite a shared branch, use `--force-with-lease`, which fails when the remote branch isn't where you last saw it, and tell your team before you press enter.
