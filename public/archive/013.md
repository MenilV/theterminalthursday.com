# 🗞️ Issue #013: The Observability Oracles: Logs, Metrics and Traces Without the Datadog Bill

![The Terminal Thursday](https://images.vialoops.com/cmpfndk6x026w0jvslad39ftq/cmv8yi3q00f3w0j044w2njxiz.jpg)

Every request your service handles leaves exhaust behind: a few log lines, a handful of spans, a nudge on a dozen counters. Multiply that by every pod and every deploy, and telemetry becomes the one dataset that grows with your traffic instead of your headcount. If the meter is per gigabyte, per host or per custom metric, the incentives go sideways: somebody deletes the debug logs, somebody else drops the high-cardinality label, and the first incident that needs exactly that detail finds it gone. Nobody budgets for that conversation, but it tends to land in the same thread as the invoice. This isn't a takedown of any single vendor; it's an argument about who gets to set the meter.

Two things changed. OpenTelemetry made instrumentation a vendor-neutral standard: its docs describe an open-source CNCF project that works with open-source and commercial backends alike, and promise that you own the data you generate. And several open-source backends now come in shapes a small team can realistically run. SigNoz keeps all three signals in one ClickHouse columnar database, OpenObserve writes Parquet from a single Rust binary, and VictoriaMetrics ships as one dependency-free binary. Collectors like Vector and the OpenTelemetry Collector sit in front and can transform and route data before it lands. None of this is free, because you inherit the disks, the upgrades and the pager, but at least the meter is yours.

Grab your coffee. Open your terminal. Let's start hacking.

## 🔬 The Sandbox: 3 Projects I Tested This Week

### 1. SigNoz 🔭 *(Full-Stack Observability)*

![SigNoz](https://images.vialoops.com/cmpfndk6x026w0jvslad39ftq/cmw1w17y42sq80jxi363ihz5k.png)

**What is it?** SigNoz is an open-source observability platform built on OpenTelemetry that keeps logs, metrics and traces in a single ClickHouse columnar database behind one UI, so you can pivot from a slow trace to the logs and metrics around it. The self-hosted stack is five containers (ClickHouse, ClickHouse Keeper, PostgreSQL for metadata, an OpenTelemetry-based collector and the SigNoz server), installed with the project's Foundry tool. The code is MIT outside the `ee/` and `cmd/enterprise/` directories, which carry a separate Enterprise license; the company also offers a hosted Cloud and an Enterprise tier.

**Why you should care:**  
Send OTLP from any OpenTelemetry SDK or Collector to ports 4317 and 4318 and you get APM views, a log explorer, dashboards and alerts, with metrics queryable through a query builder, PromQL or ClickHouse SQL. The README's own log benchmark claims 50% lower resource requirements than Elastic during ingestion, which is the project's number, so replay it on your own logs. Budget at least 4 GB of memory for Docker, read the curl-to-bash installer before you run it (it drops `foundryctl` in `~/.local/bin`, often missing from PATH on macOS), and note that the Noz AI assistant is Cloud-only.

**My Rating:** Full-Moon Oracle 4.7/5 ⭐  
**Website:** [github.com/SigNoz/signoz](https://github.com/SigNoz/signoz)

**💻 Get Started:**

```
u=https://signoz.io/foundry.sh && curl -fsSL $u | bash && foundryctl gen examples && cd docs/examples/docker/compose && foundryctl cast
```

### 2. OpenObserve 🔮 *(Single-Binary Observability)*

![OpenObserve](https://images.vialoops.com/cmpfndk6x026w0jvslad39ftq/cmw1w19i12sqy0jxi3va56l9x.png)

**What is it?** OpenObserve (O2) is a single Rust binary for logs, metrics and traces that stores data as Parquet files in an S3-native design and queries it with SQL, plus PromQL for metrics. It takes OpenTelemetry's OTLP natively, so SDKs and Collectors can send straight to it. The open-source edition is AGPL-3.0; SSO, advanced RBAC, audit trails and federated search sit in a separate Enterprise edition under a commercial license.

**Why you should care:**  
The README claims up to 140x lower storage cost than Elasticsearch, with better queries on about a quarter of the hardware; those are the project's own comparisons, so replay your own logs first. Ingest-time pipelines can enrich, redact or reduce data before it's stored, and the FAQ says there are no shards, replicas or heap sizes to manage. The catch: ingested data is immutable and only whole retention periods can be dropped, so think twice before sending it personal data. The command below is the README's quick start: open `localhost:5080` and log in with the root account it creates, and swap that example password before anything real reaches it.

**My Rating:** Parquet Prophet 4.6/5 ⭐  
**Website:** [github.com/openobserve/openobserve](https://github.com/openobserve/openobserve)

**💻 Get Started:**

```
E=root@example.com && P=Complexpass#123 && docker run -d --name openobserve -v $PWD/data:/data -p 5080:5080 -e ZO_ROOT_USER_EMAIL=$E -e ZO_ROOT_USER_PASSWORD=$P openobserve/openobserve:latest
```

### 3. VictoriaMetrics 📈 *(Time-Series Database)*

![VictoriaMetrics](https://images.vialoops.com/cmpfndk6x026w0jvslad39ftq/cmw1w1aqc2rtx0jz656yy2okq.png)

**What is it?** VictoriaMetrics is a time-series database and monitoring solution written in Go under the Apache 2.0 license, shipped as a dependency-free single-node binary configured through command-line flags, with a cluster version that is open source too. It scrapes Prometheus exporters, accepts Prometheus remote write, and also ingests InfluxDB, Graphite, OpenTSDB, Datadog agent and OpenTelemetry metrics. You query it with PromQL or its own MetricsQL, in a built-in UI at `localhost:8428/vmui`; the Homebrew service scrapes itself every 10 seconds, so there is data to look at within seconds.

**Why you should care:**  
Point an existing Prometheus at it with remote write and keep your exporters, dashboards and alert rules; the README pitches it as long-term storage for Prometheus, or a drop-in replacement for Prometheus and Graphite in Grafana. Its own benchmarks claim up to 7x less RAM and 7x less storage than Prometheus, Thanos or Cortex, a cost lever you can test in an afternoon. It covers metrics only: logs and traces have sibling projects, VictoriaLogs and VictoriaTraces, and downsampling, multiple retentions and anomaly detection are Enterprise features.

**My Rating:** Seer of Series 4.8/5 ⭐  
**Website:** [github.com/VictoriaMetrics/VictoriaMetrics](https://github.com/VictoriaMetrics/VictoriaMetrics)

**💻 Get Started:**

```
brew install victoriametrics && brew services start victoriametrics
```

## ☕ The Curious Non-Dev: No Code Required

**What is the difference between logs, metrics and traces?**

Picture a courier company. A metric is a number on the depot wall: parcels handled per hour, average delivery time, vans currently out. OpenTelemetry defines it as a measurement captured at runtime, and because it's just a number, it's usually small to keep. A log is the driver's notebook, one timestamped entry per event, such as "door locked, left with neighbour". It holds the detail, but only if you know which notebook to open. A trace is the tracking page for one parcel: every hop in order, with how long it sat at each, or in OpenTelemetry's words, the path of a request through your application.

You use them as a chain. The metric tells you something is wrong: delivery times doubled at 14:00. The trace of one slow parcel tells you where: it sat for 40 minutes at a single depot. That depot's notebook for those 40 minutes tells you why: the scanner kept crashing. Tools link the three by stamping trace and span IDs onto log lines, which an active OpenTelemetry SDK does automatically for your existing logs. It also explains where the volume comes from. Metrics grow with the number of distinct series you create, while logs and traces record individual events and grow with traffic.

## 📡 The Radar: 12 More Oracles for Your Stack This Weekend

### 📊 Metrics & Dashboards

1. [prometheus/prometheus](https://github.com/prometheus/prometheus) (~66.8k Stars) - A CNCF project that pulls metrics over HTTP from your targets and stores them as time series defined by a metric name plus key/value dimensions; each server node is autonomous, with no distributed storage to run.
2. [grafana/grafana](https://github.com/grafana/grafana) (~77.6k Stars) - The dashboard layer for metrics, logs and traces, where each query picks its own data source so one graph can mix them; licensed AGPL-3.0-only, with some Apache-2.0 exceptions.
3. [perses/perses](https://github.com/perses/perses) (~2.5k Stars) - A CNCF sandbox dashboard tool built around an open dashboard specification, with Go and CUE SDKs for dashboards-as-code and data sources for Prometheus, Tempo, Loki and Pyroscope.
4. [netdata/netdata](https://github.com/netdata/netdata) (~81.2k Stars) - Per-second metrics with zero configuration and unsupervised ML anomaly detection; the Agent is GPLv3+, but the README calls the dashboard UI closed-source, if free to use.

### 📜 Logs, Traces & Pipelines

5. [grafana/loki](https://github.com/grafana/loki) (~29.1k Stars) - Prometheus-style log aggregation that indexes only a set of labels per log stream, not the log text itself, which the README says makes it simpler to operate and cheaper to run.
6. [jaegertracing/jaeger](https://github.com/jaegertracing/jaeger) (~23.3k Stars) - Distributed tracing created at Uber and graduated at the CNCF in October 2019, with an all-in-one build that bundles the UI, collector, query service and in-memory storage.
7. [vectordotdev/vector](https://github.com/vectordotdev/vector) (~22.8k Stars) - A Rust pipeline that collects, transforms and routes logs and metrics to any backend; the README lists cutting observability costs as a use case and says Datadog's open-source team maintains it.
8. [open-telemetry/opentelemetry-collector](https://github.com/open-telemetry/opentelemetry-collector) (~7.7k Stars) - The vendor-agnostic binary that receives, processes and exports traces, metrics and logs, so you don't run a separate agent for every data format; one codebase deploys as an agent or as a collector.

### 🚨 Uptime & Alerting

9. [louislam/uptime-kuma](https://github.com/louislam/uptime-kuma) (~93.0k Stars) - A self-hosted uptime monitor with a reactive UI, 20-second check intervals, status pages you can map to your own domains and 90+ notification services.
10. [TwiN/gatus](https://github.com/TwiN/gatus) (~12.4k Stars) - A developer-oriented health dashboard where YAML conditions such as a 200 status and a response time under 300 ms decide whether an endpoint is healthy, paired with alerts to Slack, PagerDuty and more.
11. [healthchecks/healthchecks](https://github.com/healthchecks/healthchecks) (~10.5k Stars) - Cron monitoring in reverse: your jobs ping it over HTTP or email, and when a ping doesn't arrive on time it alerts you; a BSD-licensed Django app that also runs as a hosted service.
12. [keephq/keep](https://github.com/keephq/keep) (~12.5k Stars) - An alert management layer that pulls alerts from your monitoring tools into one pane, with deduplication, correlation, enrichment and workflows; MIT-licensed outside its ee/ directory.

## 🏗️ Closing Thoughts

Read the licenses before the feature lists. SigNoz and Keep put an `ee/` directory under a separate license, OpenObserve and VictoriaMetrics both offer commercial Enterprise editions with extra features, and Netdata's README calls its dashboard UI closed-source but free to use. None of that is a scandal, since the free parts do real work, but it tells you what you can fork if the roadmap and your needs ever part ways.

The durable move sits upstream of any backend. Instrument with OpenTelemetry, put a Collector or Vector in front, and decide there what gets kept, sampled or dropped. Then the backend is a replaceable part, and the day a license, a price or a maintainer changes, you rewrite a config file instead of every service. Running it yourself isn't free either: you take on the disks, the upgrades and the 3 a.m. page that a vendor used to absorb, so count those hours before you count the savings.
